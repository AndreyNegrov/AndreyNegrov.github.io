# План: сетевая кооперативная версия Neon Fortress (Firebase Realtime)

## Решения по требованиям

1. **Вход**: без аккаунтов, только по ссылке (clientId в sessionStorage).
2. **Волны**: по таймеру каждые 15 секунд, кнопки «Send Wave» нет.
3. **Золото**: у каждого свой счёт; деньги за убийство получает тот, чья башня нанесла убийственный урон (goldHost / goldGuest).
4. **Снаряды**: показывать у обоих; чужие снаряды — другим цветом.
5. **Скорость**: кнопка скорости убрана полностью.
6. **Хост**: всегда создатель комнаты.
7. **Имена**: не показывать.

---

## Текущее состояние
- Один файл `game.html`: canvas, башни (5 типов), волны врагов, снаряды, частицы.
- Состояние: `gold`, `lives`, `waveNum`, `waveActive`, `gameOver`, `towers[]`, `enemies[]`, `projectiles[]`, `particles[]`.
- Нет сборки: чистый HTML/JS.

---

## Цель
Два игрока в одной комнате: общие жизни, общая карта башен, **отдельное золото у каждого**. Синхронизация через **Firebase Realtime Database**.


---

## Архитектурный выбор: «хост + клиент»

- **Один клиент = хост**: ведёт игровой цикл (`update()`), пишет в Firebase состояние: золото, жизни, волна, башни, враги, game over.
- **Второй клиент**: подписан на Firebase, только рисует и шлёт **намерения** (поставить башню, апгрейд, продать, отправить волну).
- Хост применяет намерения (проверка золота, валидность клетки и т.д.) и обновляет состояние в Firebase.

**Почему так:** в браузере нет общего «сервера». Детерминированная симуляция на двух клиентах (одинаковый RNG и порядок) в JS сложна и хрупка. Один хост даёт один источник правды и простые правила.

## Этапы реализации

### 1. Подключение Firebase
- Добавить Firebase SDK (Realtime Database + Auth).
- Настройка проекта в Firebase Console: включить Realtime Database и при необходимости Auth (анонимный или по почте).
- В коде: инициализация `firebase.initializeApp(config)`, работа с `ref` и `onValue` / `set` / `update`.

### 2. Комнаты и роли
- **Создание комнаты**: игрок A создаёт комнату → генерируется `roomId`, в БД создаётся узел `rooms/{roomId}` с полями `hostId` (clientId создателя), `guestId: null`, позже `state`, `towers`, `enemies`, `projectiles`, `intents`.
- **Присоединение**: игрок B по ссылке (`?room=roomId`) присоединяется; в `rooms/{roomId}` обновляется `guestId: clientId`.
- Роль: `hostId === myClientId` → хост, иначе — гость. Без Firebase Auth.

### 3. Синхронизация состояния (хост пишет, оба читают)
Структура в Realtime Database (минимально):

```
rooms / { roomId } /
  hostUid: string
  players: { [uid]: true }
  state:
    lives, waveNum, waveActive, gameOver, goldHost, goldGuest, nextWaveAt
  towers: { [towerId]: { ..., ownerId: 'host'|'guest' } }
  enemies: ...
  projectiles: { [projId]: { ..., ownerId: 'host'|'guest' } }
  intents: от гостя (placeTower, upgradeTower, sellTower)
```

- Золото при убийстве: начисляется goldHost или goldGuest в зависимости от tower.ownerId.

- Хост раз в N мс (или каждый кадр, с троттлингом) делает `update(ref(rooms, roomId), { state, towers, enemies })`.
- Оба клиента подписаны на `rooms/{roomId}` и при изменении обновляют локальные переменные и перерисовывают сцену (без своего `update()` симуляции на втором клиенте).

### 4. Намерения (intents) от второго игрока
- Узел `rooms/{roomId}/intents` (или `pendingIntents`) для действий второго игрока:
  - `placeTower: { typeId, col, row }`
  - `upgradeTower: { towerId }`
  - `sellTower: { towerId }`
  - `sendWave: true`
- Второй клиент при действии пишет intent в Firebase (с `uid` и timestamp для дедупликации).
- Хост в своём `update()` раз в кадр (или по таймеру) читает новые intents, применяет их к состоянию (трата золота, проверка пути/клетки и т.д.), обновляет `state`/`towers`/`enemies` и удаляет обработанный intent.

### 5. Разделение кода на хосте и клиенte
- **Хост**: как сейчас — полный цикл: обработка клика (свои действия + применение intents), `update(dt)`, отрисовка, запись в Firebase.
- **Клиент**: только подписка на Firebase, применение полученных `state`/`towers`/`enemies` к локальным переменным, отрисовка, обработка кликов → запись intents (не вызов `update()` симуляции).

### 6. Волны и враги
- Волны по таймеру: каждые 15 секунд (после старта игры и после окончания предыдущей волны) хост автоматически запускает следующую волну. Кнопки «Send Wave» нет.
- Спавн врагов на хосте (`spawnWaveEnemies`), данные врагов в Firebase.

### 7. Снаряды и частицы
- **Снаряды**: хост пишет их в Firebase с полем `ownerId` ('host' | 'guest'). Оба клиента рисуют снаряды; свои — цветом типа башни, чужие — другим цветом (например приглушённый или отдельный оттенок).
- **Частицы**: локально на каждом клиенте.

## Настройка Firebase

1. Создай проект в [Firebase Console](https://console.firebase.google.com).
2. Включи **Realtime Database** (правила можно временно сделать `".read": true, ".write": true` для теста).
3. В настройках проекта скопируй конфиг веб-приложения (apiKey, authDomain, databaseURL, projectId, storageBucket, messagingSenderId, appId).
4. В `game.html` замени объект `FIREBASE_CONFIG` на свой конфиг (в начале скрипта, после подключения Firebase SDK).
5. Открой игру по HTTP/HTTPS (или через локальный сервер). Создай комнату и отправь ссылку второму игроку.

### 8. UI и вход в игру
- Экран «Создать комнату» / «Войти по коду (или ссылке)».
- После входа в комнату — показ «Ожидание второго игрока» или «Играем» и общий игровой экран.
- Магазин башен и апгрейд у обоих; у гостя действия уходят в intents. Кнопки скорости и Send Wave нет.

### 9. Завершение игры и перезапуск
- При `gameOver` хост пишет это в `state`; оба видят экран Game Over.
- Кнопка «Играть снова»: intent от любого → хост вызывает `initGame()` и перезаписывает `state`/`towers`/`enemies` в Firebase.

### 10. Офлайн и переподключение
- При отвале хоста: второй игрок не может продолжать (нет обновлений). Варианты: показ «Хост отключился», возможность перевыбора хоста через правила Firebase или повторное создание комнаты.
- При отвале второго игрока: хост продолжает один; можно очищать его intents и показывать «Игрок вышел».
